# 示例材料使用说明

本目录提供一套可直接上传到「核查镜」的演示材料，用于功能验证与答辩演示。三份文档均为**虚构教学样例**，不含真实个人信息、真实仓库地址或 API 密钥。

## 一、文件清单

| 文件 | 角色 | 说明 |
| --- | --- | --- |
| `示例任务书-Web前端开发课程实训.md` | 规则源（任务书） | 与 `src/lib/sample.ts` 中 `SAMPLE_TASK_TEXT` **逐字一致**，共 7 条，其中 5 条是可核查要求 |
| `示例报告A-校园二手书交易平台（待改进版）.md` | 被核查报告 | 与 `SAMPLE_REPORT_TEXT` **逐字一致**，刻意留有缺项，用于演示问题检出 |
| `示例报告B-实验室设备预约管理系统（完整版）.md` | 被核查报告 | 结构、技术、成果物、篇幅均齐备，用于演示高覆盖率对照 |

> 用词说明：任务书原文使用「实践报告」，因此两份报告标题也统一为「实践报告」，避免标题口径不一致干扰演示讲解。

## 二、与内置「离线演示」的关系

界面右上角的「离线演示」按钮加载的是 `src/lib/sample.ts` 里的内置数据，其任务书与**报告 A** 完全相同。因此：

- 点「离线演示」= 直接看到报告 A 的核查结果；
- 配置好模型接口后，上传「任务书 + 报告 A」，真实链路应得到与离线演示一致的结论分布。

这个"同一份材料、两条链路"的设计，可以在答辩时用来说明证据链校验不是写死的假结果。

## 三、预期核查结论（用于自检）

| 要求项 | 报告 A 预期 | 报告 B 预期 | 判定依据 |
| --- | --- | --- | --- |
| Q1 五个章节完整 | 部分满足 | 已覆盖 | A 缺「总结」；B 五章齐全 |
| Q2 技术栈与 ≥3 页面 | 已覆盖 | 已覆盖 | A：Vue 3 + 3 页面；B：React 18 + 4 页面 |
| Q3 源码仓库与 README | 已覆盖 | 已覆盖 | 两份报告均写明 Gitee 仓库与根目录 README |
| Q4 正文 ≥3000 字 | 存在矛盾 | 已覆盖 | A 自述"全文约 2200 字"；B 自述"约 3600 字" |
| Q5 ≥3 张截图并逐张说明 | 缺失 | 部分满足* | A 全文无附图内容；B 有 3 张图的逐张文字说明 |

\* 报告 B 的附图部分仅含逐张文字说明，Q5 预期为「部分满足」。模型输出受温度与措辞影响，具体状态可能略有浮动，但**证据引用必须能在报告原文中命中**，否则会被 `validateResults` 丢弃或降级。

> 关于字数：报告 A 的"全文约 2200 字"与报告 B 的"正文约 3600 字"是**报告自身对篇幅的声明**，属于被核查材料的内容，用于触发 Q4 判定。报告 B 实际正文约 3600 汉字，声明与事实一致；报告 A 为与内置离线演示数据逐字一致而保持精简，其声明既低于任务书下限（这是要被检出的矛盾点），也高于实际篇幅，正好模拟"报告扩充后未同步更新字数自述"的常见情形。核查引擎比对的是"报告怎么声明"与"任务书怎么要求"，不会替报告数字数，这一点在答辩时要讲清。

## 四、演示操作步骤

1. 双击 `一键启动.bat`，浏览器打开 `http://localhost:5173`。
2. 左侧上传 `示例任务书-Web前端开发课程实训.md`，右侧上传 `示例报告A-…md`（也可用「直接粘贴文字」）。
3. 点「开始核查」，观察左下角三阶段时间线与流式输出。
4. 在核查矩阵中逐条查看四态结论，**点证据引用可跳转到右侧报告原文并高亮**，重点演示 Q4「矛盾」与 Q5「缺失」。
5. 导出 Markdown 核查报告，作为修改建议清单。
6. 换成报告 B 再跑一次，对比覆盖率提升，形成"发现问题 → 修改 → 复核"的完整叙事。

若需在无网络环境下演示，第 2–3 步改为点「离线演示」，其余步骤相同。

## 五、格式说明

项目 `parseFile()` 原生支持 `PDF / DOCX / TXT / MD`，本目录采用 `.md`，双击可读、上传即用、也方便复制粘贴。若需要 Word 或 PDF 版本，把内容另存为对应格式即可，核查结论不受影响。
