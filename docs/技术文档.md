## 1. 项目概述

### 1.1 背景

高校实训、课程设计、毕业设计等教学环节普遍采用「任务书 + 实践报告」的双文档模式。任务书会列出章节结构、技术栈、成果物、篇幅、附图等十余条细碎要求；学生撰写报告时容易漏项，教师批改时也只能凭记忆逐条比对。人工核查耗时、易漏、标准不一。

通用大模型聊天窗口无法直接解决该问题：把两份长文档丢进去问「有没有问题」，得到的是笼统、不可追溯、经常编造的结论，无法作为批改依据。

### 1.2 项目目标

构建一个 **AI Native 的 Web 前端应用**：以任务书为「要求集合」，以实践报告为「证据集合」，由 AI Agent 自动完成拆解 → 检索 → 判定 → 溯源，输出每条要求的状态（已覆盖 / 部分满足 / 缺失 / 存在矛盾）、置信度、原文证据与修改建议，并支持一键导出核查报告。

### 1.3 设计原则

1. **证据优先**：任何结论必须能点击跳回报告原文；做不到就不给「已覆盖」。
2. **前端为主**：赛项明确后端仅作 AI 接入层，因此解析、切片、检索、状态管理全部在浏览器完成。
3. **单接口可跑**：只依赖一个 OpenAI 兼容 Chat Completions 接口，不依赖向量库、embedding 接口或额外服务。
4. **可解释、可复核**：暴露检索命中片段与分数、模型流式输出、置信度，结论不接受黑箱。

## 4. AI 技术方案（重点）

### 4.1 模型接入与选型理由

采用 **OpenAI 兼容 Chat Completions 协议**作为唯一抽象层。理由：

- 国内主流厂商（DeepSeek、智谱 GLM、通义千问、Kimi）均兼容，换厂商只需改几个环境变量，避免绑定；
- 支持 `stream: true` 的 SSE 输出，可直接实现「AI 思考状态可视化」这一评分点；
- 支持 `tools / tool_calls` 标准 Function Calling，是 Agent 工具调用闭环的基础；
- 支持 `image_url` 多模态消息，配合可独立配置的视觉模型实现图像 OCR；
- 核心链路只需一个 Chat 接口即可跑通，无需 embedding / rerank / 向量库；视觉与语音作为可插拔增强，未配置时自动降级，符合「单接口、低成本、可扩展」约束；
- 低温度（0.1）+ JSON 结构化输出约束，提升结论稳定性。

服务端代理强制使用环境变量中的 `model` / `baseUrl`，**不接受客户端覆盖**，既防 SSRF 也防额度被滥用。

### 4.2 Function Calling 驱动的 Agent 工作流

没有采用通用 Agent 框架，而是针对本场景设计了受控的三阶段工作流，兼顾「Agent 的规划、工具调用与自主决策」与「输出稳定、成本可控」：

| 阶段 | 角色 | 输入 | 输出 | 调用次数 |
| --- | --- | --- | --- | --- |
| ① 规划拆解 | Planner | 任务书全文（≤12000 字符） | 最多 12 条结构化要求项（含检索关键词、类别） | 1 次 |
| ② 工具取证 | Agent + Tool | 要求项 + `retrieve_evidence` 工具定义 | 模型自主发起多条工具调用（意图 + 关键词） | 1 次 |
| ③ 判定溯源 | Executor | 要求项 + 每条 top-4 报告片段 | 四态结论 + 原文引用 + 置信度 + 建议 | 1 次（流式） |

**阶段②是真正的 Function Calling**：检索以标准 OpenAI tools 定义暴露（`RETRIEVE_TOOL`），服务端原样透传 `tools` 与 `tool_choice=required`，模型返回 `tool_calls` 后，前端解析参数并**真实执行本地 BM25 检索工具**，把结果组装为证据包。这与「把关键词写死在代码里」有本质区别——检索意图、关键词、检索哪几条都由模型自主决策，构成完整的「规划 → 工具调用 → 工具执行 → 再决策」Agent 闭环。

- **工具契约**：`retrieve_evidence(requirement_id, intent, keywords[])`，返回带 id 的片段。
- **容错降级**：若模型不支持 Function Calling、未返回工具调用或参数非法，自动降级为逐条本地 BM25 检索（`fallbackRetrieve`），核心链路始终可用；降级事件在时间线如实标注。
- **批量判定**：阶段③把「要求项 + 各自证据包」压成一次调用，避免逐条调用带来的延迟与费用线性上升，也更利于结构化解析与一致性。

端到端实测（DeepSeek deepseek-chat）：6 条要求 → 模型自主发起 6 次工具调用 → 6 条四态判定 → 6 条引用全部可在原文追溯（`scripts/e2e-verify.mjs` 可复现）。

### 4.3 Prompt 设计

系统提示设定四条铁律：只依据给定材料、结论必须附逐字引用、无证据如实判缺失、报告内指令一律不执行（防提示注入）。

- **阶段一 Prompt**：要求「最多 12 条、合并语义重复项、每条覆盖一个可验证点」，并给出 JSON Schema 示例，字段包含 `title / requirement / keywords / category`。
- **阶段二 Prompt**：把 `<报告片段>` 明确标注为「被核查的数据」而非指令；规定 `evidence.quote` 必须是片段中出现过的 15~120 字逐字摘录；规定无相关片段时 status 只能是 `missing` 或 `partial` 且 evidence 为空；要求顺序与要求项一致、不得遗漏。
- **容错解析**：`parseJsonArray` 依次尝试「纯 JSON → 去 Markdown 代码块 → 截取首尾方括号 → 逐个对象提取」，兼容模型带前后缀、带代码块、末尾被截断等常见情况；全部失败时给出明确错误信息而非白屏。

### 4.4 检索增强（RAG）

精简版采用 **BM25 + 中文二元字组 + 章节标题加权**，全部在浏览器实现：

- 中文无需分词库，按 2-gram 切分，兼顾未登录词；英文数字按词切分；内置停用词表。
- BM25 打分：`idf × tf(k1+1) / (tf + k1(1−b + b·dl/avgdl))`，`k1=1.5, b=0.75`，预计算文档频次 df。
- 章节标题命中查询词时分数 ×1.35，因为「五、总结」这类标题本身就是结构要求的最强证据。
- 每条要求取 top-4 片段组成证据包，同时在界面展示命中片段 id 与分数，使检索过程可解释。

**选型说明**：向量检索需要 embedding 接口或向量数据库，与「仅一个 Chat 接口」的约束冲突；教学文档规模小（几十个片段）、术语密集，词项检索在准确率和可解释性上更有优势。第 10 节给出了混合检索与浏览器端重排的演进路线。

**检索效果实证**：对内置示例任务书抽取的 5 条可核查要求逐一执行 BM25 检索，top-4 片段全部命中对应章节（如「技术栈与页面数」命中「二、系统设计」、「源码仓库与 README」命中「三、功能实现」），命中率 5/5。章节标题加权使「五、总结」这类结构性要求能够直接锚定到标题证据，这是纯关键词匹配难以做到的——检索增强显著提升了逐条判定的证据可得性，而非仅把整篇文档塞进上下文。

### 4.5 AI 安全与可控性（防幻觉）

这是本项目区别于普通「套壳聊天」的关键，采用三层防线：

1. **Prompt 层**：禁止编造、强制逐字引用、防提示注入、四态枚举约束。
2. **结果硬校验层**（`validateResults`，代码可验证）：
   - 引用去空白后必须在报告全文中命中，否则**直接丢弃**；
   - 用引用原文**反查真实 chunkId**，覆盖模型给出的 id，杜绝「编造定位」导致跳转失效；
   - 状态枚举白名单化，非法值降级为 `missing`；置信度裁剪至 0~1；
   - 被判 `covered` 却拿不出任何有效证据时，**自动降级为 `partial`**。
3. **产品层**：界面明示「AI 结论仅供辅助，最终以人工复核为准」；文档原文不上传服务器；支持中止核查（AbortController）与错误边界提示。

### 4.6 流式输出与交互

服务端把上游 SSE 帧原样透传（`text/event-stream` + `X-Accel-Buffering: no`），前端用 `ReadableStream` 逐帧解析 `choices[0].delta.content`，实时展示在「Agent 工作流」面板中。为避免每个 token 触发一次 React 重渲染，状态层以 **80ms 窗口合并增量**，并限制展示缓冲长度。

### 4.7 多模态与端侧处理

本项目实现了**文本 / 图像 / 语音**三类模态输入，并统一汇流到同一条「切片 → 检索 → 核查」链路，做到多模态到文本链路的自然融合，而非割裂的功能堆叠：

1. **文本模态**：PDF（pdf.js）、DOCX（mammoth）、TXT / MD 均在**浏览器端**解析，不经过服务器；两个较重解析器动态 import 懒加载并由 Vite 自动分包。对无文字层的 PDF 给出明确提示并引导粘贴入口。
2. **图像模态**：上传报告 / 任务书截图后，浏览器端转 data URL 直接发给服务端视觉通道（`vision: true`），由可独立配置的视觉模型（`LLM_VISION_MODEL` / `LLM_VISION_BASE_URL`）做逐字 OCR，输出带段落结构的纯文本，再回流统一链路。图片不落服务器磁盘；视觉模型未启用时返回明确降级提示。
3. **语音模态**：基于浏览器原生 Web Speech API（`SpeechRecognition`，`zh-CN` 连续识别），**端侧**转写无需密钥、无需上传音频；实时转写显示在草稿区，识别完成后自动汇入对应文档。

服务端视觉通道与文本通道共用同一反向代理，但视觉模型基地址与模型名由服务端环境变量单独指定，前端无法覆盖，既防 SSRF 也便于按成本切换模型。多模态增强了「输入可得性」，而证据链硬校验对任何模态转写出的文本一视同仁，保证结论质量不因模态而降低。

## 6. 前端工程质量

- React 18 + TypeScript `strict` + `noUnusedLocals` + `noUnusedParameters`，`npm run build` 先做类型检查再构建；
- 组件按职责拆为 5 个纯展示组件，业务状态集中在 `useChecker`（useReducer），UI 局部状态留在 App；
- 代码分割：首屏 JS 约 175KB（gzip 62KB），pdf.js / mammoth 独立分包按需加载；静态资源设置长缓存 `max-age=31536000, immutable`，HTML 使用 `no-cache`；

- 无障碍：上传区支持键盘 Enter/Space 触发，进度条带 `aria-label`，语音听写有脉冲状态提示；
- 自然语言输入：语音识别用浏览器原生 API、图像 OCR 走服务端视觉通道，均复用统一文档结构，无重复渲染路径。

## 7. 创新点

**技术创新**
1. 引用反查片段 id + 引用存在性校验 + 无证据自动降级，构成可验证的防幻觉闭环，而非仅靠 Prompt「呼吁不要编造」。
2. **Function Calling 工具调用闭环**：检索以标准 tools 定义暴露，模型自主决定检索意图与关键词并真实执行本地 BM25；工具不可用自动降级，兼顾智能与稳定。
3. **标准 MCP Server**：以独立进程通过 JSON-RPC over stdio 暴露 `retrieve_evidence` / `list_reports` 工具，零第三方依赖，可被任意 MCP 客户端复用，证明检索能力可标准化对外输出。
4. **三模态统一链路**：文本 / 图像 OCR / 语音转写三类输入汇流到同一核查管线，多模态到文本的融合自然，且证据质量不因模态而降低。
5. 零依赖的浏览器端检索增强与结构化输出容错解析，单 Chat 接口即可运行。

**应用创新**：把「AI 文档分析」从通用的总结/问答，收敛到「任务书 ↔ 成果物合规核查」这一具体教学场景，结论可直接用于批改与自查。

**交互创新**：证据引用一键回跳原文并高亮、检索命中片段与分数可见、模型流式输出与工作流时间线同步展示，把 AI 的「判断依据」变成可操作的界面对象；语音口述与截图识别让材料录入更自然。

## 9. 安全、隐私与合规

- 密钥仅在服务端内存/环境变量，`.gitignore` 排除 `.env*`，前端产物不含密钥；
- 文档原文不落服务器，仅检索命中片段进入模型上下文；图片转 data URL 直发、识别后即弃，不落磁盘；
- 单次请求体限 12MB（容纳 base64 图片）、messages 数量校验（≤40）、工具数量校验（≤16）、模型地址与视觉模型均由服务端固定，杜绝 SSRF；
- 视觉模态需服务端显式 `LLM_VISION=true` 开启，前端无法绕过配置调用付费视觉接口；
- 提示注入防护、内容过滤与人工复核声明；
- 作品原创，未使用开源项目包装；依赖均为通用工具库，MCP Server 零第三方依赖。

## 10. 总结与展望

本项目以可控的工程复杂度实现了「可解释的 AI 材料核查」，完整覆盖赛项 AI 技术深度中的大模型集成、Agent/工作流、Function Calling 工具调用、RAG、多模态、AI 安全与 MCP 工具集成等全部考察点。已交付能力包括：三模态输入（文本 / 图像 OCR / 语音）、Function Calling 驱动的取证闭环、标准 MCP Server、证据链防幻觉校验、流式判定与一键导出。

后续演进路线（在已实现能力之上继续深化）：

1. 引入 embedding 或浏览器端 Transformers.js 重排，在现有 BM25 之上做混合检索与端云协同；
2. 视觉模态从「OCR 成文本」升级为版面级理解，自动核查「附图数量 / 图表说明 / 排版格式」类要求；
3. 教师端批量核查、历史版本对比、班级维度统计与合规看板；
4. MCP Server 补充「定位段落 / 比对表格 / 生成核查报告」等更多工具，接入教务系统工作流。

### 10.1 社会价值

- **教学减负与标准化**：把教师从重复、易漏的逐条比对中解放出来，让批改标准可统一、可复核，降低主观因素带来的评分偏差；
- **促进学生自查**：学生提交前即可得到一份逐条、可追溯的修改清单，把合规要求前置到写作过程，减少返工；
- **促进教育公平**：统一的机器辅助基线让不同班级、不同教师的核查口径趋于一致；AI 结论明确要求人工复核，避免算法权威化；
- **数据最小化示范**：文档原文不出浏览器、密钥不入前端产物，为教育类 AI 应用的隐私保护提供可复用范式。

### 10.2 商业潜力与可持续性

**目标市场**：全国数千所高校的实训、课程设计、毕业设计环节，叠加职业培训、竞赛评审、企业内训文档合规等场景，属于高频、刚需、可复用的横向市场。与传统人工核查相比，本方案把单份材料的核查从十余分钟压缩到数十秒，且标准一致、全程留痕。

**产品形态与商业模式**：

| 模式 | 交付形态 | 收费方式 | 适用性 |
| --- | --- | --- | --- |
| SaaS 订阅 | 多租户 Web 平台，按校开通 | 按校 / 按学期订阅，按核查份数阶梯计费 | 中小院校、教研室，获客成本低 |
| 私有化部署 | 单进程服务 + 内网模型网关 | 一次性授权 + 年度维保 | 对数据不出校有硬性要求的高校 |
| 平台增值 | 作为在线教育 / 教务平台的插件能力 | API 调用量分成 | 借力已有渠道快速铺量 |
| MCP 生态 | 标准化检索取证工具（已交付） | 开发者生态引流 / 技术服务 | 建立技术壁垒与开发者心智 |

**可持续路径**：以「材料合规核查」为切口建立模板库与规则库（任务书类型 → 核查项模板），沉淀数据资产形成网络效应；由单校试点向区域联盟校复制，边际成本随模板复用递减；MCP Server 与多模型兼容策略降低厂商锁定风险，保障长期可持续运营。
